## 1. 引擎技术栈

### 1.1 核心组件

- **宿主语言**: C# (.NET)
- **模块系统**: CommonJS + 自定义eval模式
- **安全机制**: 沙箱隔离 + 权限控制

    // 2. 加载JavaScript代码

    }
}

#### 4.3.2 BGI模块加载的根本限制与技术突破

**重大技术发现** (基于AutoCommission项目研究，2025.07.24): 通过深入分析BGI源码和对比工作脚本，发现BGI ClearScript V8引擎对JavaScript变量声明和eval模块加载有严格的技术要求。

**核心技术突破**: const vs var声明的根本性差异
```javascript
// ✅ var声明 - 可以跨作用域访问
eval('var Constants = { VERSION: "1.0.0" };');
log.info("Constants类型: " + typeof Constants); // "object" - 成功！

// ❌ const声明 - 无法跨作用域访问  
eval('const Constants = { VERSION: "1.0.0" };');
log.info("Constants类型: " + typeof Constants); // "undefined" - 失败！
```

**实验验证结果** (来自AutoCommission项目测试):
```
✅ var声明模块: Constants(var)类型: object, Constants.VERSION: 0.98.11
❌ const声明模块: Constants(const)类型: undefined
✅ var基础类型: TEST_VAR类型: string, TEST_VAR值: test_var_value
❌ const基础类型: TEST_CONST类型: undefined, TEST_CONST访问失败
✅ function声明: testFunction类型: function, testFunction调用: function_works
❌ const对象: TEST_OBJECT类型: undefined, TEST_OBJECT访问失败
```

**ClearScript V8的eval机制**:
```csharp
// BGI源码: ScriptProject.cs:92
await (Task)engine.Evaluate(code);
```

当`engine.Evaluate(code)`执行时，整个main.js在一个执行上下文中运行。eval函数的变量注入行为严格依赖于**调用时的作用域层级**。

**作用域层级图**:
```
engine.Evaluate(main.js) -- 根执行上下文
├── 顶层作用域 (Top-level Scope)
│   └── eval(...) ✅ 变量成为真正的全局变量
├── 函数作用域 (Function Scope)  
│   └── eval(...) ❌ 变量只在函数内可见
├── try-catch作用域 (Try-catch Scope)
│   └── eval(...) ❌ 变量只在try块内可见
└── IIFE作用域 (IIFE Scope)
    └── eval(...) ❌ 变量只在IIFE内可见
```

**对比分析 - 工作脚本vs问题脚本**:

**✅ 工作脚本 (`GeniusInvokationTCGQuickProficiency/main.js:1`)**:
```javascript
eval(file.readTextSync("lib/ocr.js")); // 直接顶层执行
// 函数waitForTextAppear和recognizeTextAndClick成为全局可用
```

**❌ 问题脚本 (AutoCommission之前的版本)**:
```javascript
// 任何形式的包装都会失败：
try { eval(...); } catch {}           // try-catch包装
(function() { eval(...); })();        // IIFE包装
function load() { eval(...); } load(); // 函数包装
```

**根本原因**:
1. **引擎限制**: ClearScript V8的eval变量注入严格按照JavaScript标准的词法作用域规则
2. **全局要求**: 只有在真正的顶层作用域执行的eval才能创建全局变量  
3. **无法变通**: 没有任何JavaScript技术可以突破这个引擎级别的限制

**实验验证**:
```javascript
// 测试脚本 - 验证作用域行为
eval('var topLevel = "global";'); // 顶层执行
log.info("顶层变量: " + typeof topLevel); // "string" - 成功

(function() {
  eval('var funcLevel = "local";'); // 函数内执行
})();
log.info("函数变量: " + typeof funcLevel); // "undefined" - 失败！

try {
  eval('var tryLevel = "block";'); // try块内执行
} catch(e) {}
log.info("try块变量: " + typeof tryLevel); // "undefined" - 失败！
```

**BGI脚本执行流程**:
1. **引擎创建**: ClearScript V8引擎实例化
2. **代码加载**: 通过`engine.Evaluate(code)`执行整个main.js
3. **作用域注入**: eval执行的代码变量注入到**当前执行上下文**

**关键发现 - 执行上下文的影响**:
```csharp
// BGI源码: ScriptProject.cs:67
await (Task)engine.Evaluate(code);
```

当main.js被`engine.Evaluate()`执行时：
- **顶层代码**: 直接在全局作用域执行，eval导入的变量成为真正的全局变量
- **IIFE内代码**: 在函数作用域执行，eval导入的变量只在该函数内可见

**作用域测试示例**:
```javascript
// 测试脚本结构对作用域的影响

// ✅ 方式1: 顶层执行（推荐）
eval(file.readTextSync("lib/utils.js"));
log.info("Utils类型: " + typeof Utils); // "object" - 成功

// ❌ 方式2: IIFE内执行（问题）
(function() {
  eval(file.readTextSync("lib/utils.js"));
  log.info("函数内Utils类型: " + typeof Utils); // "object" - 函数内可见
})();

log.info("函数外Utils类型: " + typeof Utils); // "undefined" - 函数外不可见！
```

**BGI环境的作用域规则**:
1. **eval执行上下文**: eval在哪个作用域执行，变量就注入到哪个作用域
2. **无法跨作用域**: 函数作用域内的变量无法成为真正的全局变量
3. **引擎级别限制**: 这是ClearScript V8引擎的底层行为，无法通过JavaScript代码改变

#### 4.3.3 BGI环境的JavaScript模块化开发要求

基于AutoCommission项目的技术发现，BGI环境下的JavaScript脚本必须遵循以下技术规范：

**1. 变量声明要求**:
```javascript
// ✅ 正确 - 必须使用var声明
var ModuleName = {
    method1: function() { /* ... */ },
    method2: async function() { /* ... */ }
};

// ❌ 错误 - const/let声明无法跨eval上下文
const ModuleName = { /* ... */ };  // 无法跨作用域访问
let ModuleName = { /* ... */ };    // 同样受限
```

**2. 模块加载要求**:
```javascript
// ✅ 正确 - 顶层直接eval
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));

// ❌ 错误 - 任何包装都会导致作用域隔离
try { eval(file.readTextSync("lib/module.js")); } catch {}
(function() { eval(file.readTextSync("lib/module.js")); })();
function loadModule() { eval(file.readTextSync("lib/module.js")); } loadModule();
```

**3. 脚本返回要求**:
```javascript
// ✅ 正确 - 使用IIFE包装return语句
(async () => {
    return await Main();
})();

// ❌ 错误
return Main();                 // 顶层return语句，语法错误
Main();                        // 返回VoidResult，类型转换失败
```

**BGI环境的作用域特点**:
1. **变量声明敏感**: 只有`var`和`function`声明能正确跨eval上下文
2. **执行上下文严格**: eval必须在真正的顶层作用域执行
3. **作用域隔离**: 任何函数包装都会创建作用域隔离
4. **Promise返回要求**: 脚本必须返回Promise对象供BGI引擎处理

**常见陷阱示例**:

**1. try-catch作用域隔离（新发现）**:
```javascript
// ❌ try-catch包装导致作用域隔离
try {
  eval(file.readTextSync("lib/utils.js")); // Utils在try块作用域内
} catch (error) {
  log.error("加载失败");
}
log.info("Utils类型: " + typeof Utils); // "undefined" - 无法访问！

// ✅ 正确的错误处理方式
function safeLoadModule(path, name) {
  try {
    eval(file.readTextSync(path)); // 函数内的try-catch不影响全局注入
    return true;
  } catch (error) {
    log.error("加载" + name + "失败: " + error.message);
    return false;
  }
}
safeLoadModule("lib/utils.js", "Utils"); // 顶层调用
log.info("Utils类型: " + typeof Utils); // "object" - 成功访问！
```

**2. IIFE作用域隔离（已知问题）**:
```javascript
// ❌ IIFE包装导致作用域隔离
(function() {
  eval(file.readTextSync("lib/utils.js")); // Utils在函数作用域内
})();
log.info("Utils类型: " + typeof Utils); // "undefined" - 无法访问！

// ✅ 顶层直接执行
eval(file.readTextSync("lib/utils.js")); // 直接在全局作用域
log.info("Utils类型: " + typeof Utils); // "object" - 成功访问！
```

**3. 错误的模块检查方式**:
```javascript
// ❌ 错误的模块检查方式
function checkModules() {
  if (typeof window !== 'undefined' && window.MyModule === undefined) {
    return false; // 在BGI中可能误判
  }
}

// ✅ 正确的BGI环境检查方式
function checkModules() {
  try {
    return eval('typeof MyModule') !== 'undefined';
  } catch (error) {
    return false;
  }
}
```

**执行上下文层级图**:
```
engine.Evaluate(code) 
├── 全局作用域 (Global Scope)
│   ├── eval(...) ✅ 变量注入到全局
│   ├── function() { eval(...) } ❌ 变量注入到函数作用域
│   └── try { eval(...) } ❌ 变量注入到try块作用域
└── 函数作用域 (Function Scope)
    └── try-catch块作用域 (Try-Catch Block Scope)
```

public static string NormalizePath(string root, string path)

        }

## 12. AutoCommission项目案例研究

AutoCommission项目是BGI JavaScript脚本模块化开发的标杆案例，成功解决了ClearScript V8引擎的技术限制：

**项目成果**:
- **模块化重构**: 从3067行单体文件重构为9个功能模块
- **技术突破**: 发现并解决const/var作用域问题和InvalidCastException根因
- **架构标准**: 建立BGI脚本模块化开发标准
- **实战验证**: 提供完整的技术解决方案
- **API兼容性**: 解决file.readText异步方法兼容性问题

**核心技术贡献**:
1. **变量声明规范**: 确立var声明的必要性
2. **模块加载模式**: 顶层直接eval的标准模式
3. **返回值处理**: IIFE包装Promise返回的解决方案
4. **脚本架构标准**: 发现脚本最后表达式必须返回Promise的要求
5. **API兼容性**: 统一使用同步file.readTextSync方法
6. **调试验证方法**: 模块加载状态检查机制

**关键技术发现（2025.07.25更新）**:
1. **InvalidCastException根因**: 脚本的最后一个表达式如果不是IIFE，会返回VoidResult而非Promise
2. **文件结构要求**: 必须按照"模块加载→函数定义→IIFE"的标准结构
3. **API版本兼容**: 某些BGI版本可能不支持异步file.readText方法，需使用同步版本
4. **文件写入限制**: BGI不提供异步file.writeText方法，只支持同步file.WriteTextSync
5. **API命名规范**: BGI中的方法命名遵循PascalCase（如WriteTextSync）而非camelCase
6. **常量定义完整性**: 脚本中使用的所有路径常量必须在constants.js中完整定义
7. **数据文件格式规范**: 数据文件的JSON结构必须与代码中的期望格式严格匹配

**项目参考**: `jshelp/jscode/AutoCommission/README_REFACTOR.md`
