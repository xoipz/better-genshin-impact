# BGI JavaScript脚本环境 - 不可使用的JS方法和功能

## 概述

BGI（BetterGenshinImpact）的JavaScript脚本引擎基于Microsoft ClearScript V8，运行在沙箱环境中，出于安全考虑限制了许多标准JavaScript功能。本文档详细列出在BGI脚本环境中不可使用的方法和功能。

**相关源码位置**:
- 引擎扩展: `BetterGenshinImpact\Core\Script\EngineExtend.cs:102-106`
- 安全机制: `BetterGenshinImpact\Core\Script\Dependence\LimitedFile.cs`
- 路径验证: `BetterGenshinImpact\Core\Script\Utils\ScriptUtils.cs:11-25`

---

### 3.2 BGI模块化开发的根本性限制

**重大技术发现** (基于AutoCommission项目研究，2025.07.24): BGI ClearScript V8引擎对JavaScript变量声明类型有严格限制，直接影响模块化开发。

```javascript
// ❌ 最高优先级限制：const声明无法跨eval作用域
const ModuleName = {
    method: function() {}
};
eval('var test = "hello";'); 
// ModuleName在eval执行后仍然无法访问！

// ✅ 唯一正确的方式：使用var声明
var ModuleName = {
    method: function() {}
};
eval('var test = "hello";');
// ModuleName可以正常访问
```

**实验验证结果** (来自AutoCommission项目测试):
```
✅ var声明模块: Constants(var)类型: object, Constants.VERSION: 0.98.11
❌ const声明模块: Constants(const)类型: undefined
✅ var基础类型: TEST_VAR类型: string, TEST_VAR值: test_var_value
❌ const基础类型: TEST_CONST类型: undefined
✅ function声明: testFunction类型: function
❌ const对象: TEST_OBJECT类型: undefined
```

**核心技术限制**:
1. **const声明限制**: 在BGI环境中，`const`声明的变量无法跨eval上下文传递
2. **let声明限制**: `let`声明同样受到作用域限制
3. **var声明要求**: 只有`var`和`function`声明能正确跨作用域
4. **顶层执行要求**: eval必须在真正的顶层作用域执行
```

### 3.3 BGI环境的模块化开发规范

基于AutoCommission项目的技术突破，BGI环境下的模块化开发必须遵循以下规范：

**1. 模块声明规范**:
```javascript
// ✅ 正确 - 必须使用var声明
var ModuleName = {
    method1: function() { /* ... */ },
    method2: async function() { /* ... */ }
};

// ❌ 错误 - const/let声明在BGI中无法正常工作
const ModuleName = { /* ... */ };  // 作用域限制
let ModuleName = { /* ... */ };    // 同样受限
```

**2. 模块加载规范**:
```javascript
// ✅ 正确 - 顶层直接eval
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));

// ❌ 错误 - 任何包装都会导致作用域隔离
try { eval(file.readTextSync("lib/module.js")); } catch {}
(function() { eval(file.readTextSync("lib/module.js")); })();
function loadModule() { eval(file.readTextSync("lib/module.js")); } loadModule();
```

**3. 脚本返回规范**:
```javascript
// ✅ 正确 - 使用IIFE包装return语句
(async () => {
    return await Main();
})();

// ❌ 错误
return Main();                 // 顶层return语句会导致语法错误
Main();                        // 返回VoidResult，导致类型转换失败
```

### 3.4 作用域问题的排查和解决

```javascript
// ❌ 错误的作用域检查方式
function checkModules() {
  // 在BGI环境中，window和global可能不存在
  if (typeof window !== 'undefined' && window.MyModule === undefined) {
    return false; // 错误判断
  }
}

// ✅ 正确的BGI环境作用域检查
function checkModules() {
  try {
    // 直接使用eval检查全局作用域变量
    const moduleType = eval('typeof MyModule');
    return moduleType !== 'undefined';
  } catch (error) {
    log.error('模块检查失败: ' + error.message);
    return false;
  }
}
```

**常见问题排查**:

**问题1: "Module is not defined"**
- 原因：使用了`const`声明模块
- 解决：改为`var`声明：`var ModuleName = { ... }`

**问题2: "Illegal return statement"**
- 原因：在顶层作用域直接使用return语句
- 解决：使用IIFE包装：`(async () => { return await Main(); })()`

**问题3: "Unable to cast VoidResult to Task"**
- 原因：脚本的最后一个表达式未返回Promise对象
- 解决：确保IIFE是文件的绝对最后一个表达式，所有执行逻辑都在IIFE内部

**详细分析**（基于AutoCommission项目技术发现）:
```javascript
// ❌ 错误结构 - IIFE提前结束，log语句在外部执行
(async function () {
  // 主要逻辑
})(); // IIFE结束

log.info("模块化主文件加载完成"); // 这成为脚本最后表达式，返回VoidResult！

// ✅ 正确结构 - 所有逻辑都在IIFE内部
(async function () {
  // 主要逻辑
  log.info("模块化主文件加载完成"); // 在IIFE内部
})(); // 这是文件的最后表达式，返回Promise
```

**根本原因**: BGI V8ScriptEngine期望脚本返回Promise对象用于Task转换。当log语句在IIFE外部执行时，它成为脚本的最后表达式，返回VoidResult而非Promise，导致`Unable to cast object of type 'Microsoft.ClearScript.VoidResult' to type 'System.Threading.Tasks.Task'`异常。

**BGI脚本架构标准**:
```javascript
// 1. 顶层模块加载（BGI要求）
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));

// 2. 函数定义区域（必须在IIFE之前）
async function executeMainProcess() {
  // 主要业务逻辑
}

// 3. IIFE作为最后表达式（关键）
(async function () {
  try {
    // 所有执行逻辑在此
    await executeMainProcess();
    log.info("执行完成"); // 必须在IIFE内部
  } catch (error) {
    log.error("出错: " + error.message);
    throw error;
  }
})(); // 必须是文件的绝对最后一个表达式
```

**BGI作用域特点**:
- eval导入的模块变量直接进入全局作用域
- 不应依赖window或global对象检查模块
- 使用eval('typeof ModuleName')是最可靠的检查方式
- 只有`var`和`function`声明能跨eval上下文传递

---

```javascript

// require函数

// module.exports

## 4. 文件系统访问限制

### 4.1 Node.js文件系统模块（不可用）

```javascript

### 4.2 受限的文件访问

```javascript

// [".txt", ".json", ".log", ".csv", ".xml", ".html", ".css"]

// 文件大小限制

```

**安全机制**:
- **路径限制**: 只能访问脚本项目目录内的文件
- **扩展名白名单**: 仅支持`.txt`、`.json`、`.log`、`.csv`、`.xml`、`.html`、`.css`
- **文件大小限制**: 最大999MB
- **路径遍历保护**: 防止`../`等路径遍历攻击

// lib/utils.js - 模块文件
var Utils = {

// main.js - 主入口文件

// 2. 主程序逻辑
const Main = async () => {
    try {
        log.info("版本: " + Constants.VERSION);
        await Utils.delay(1000, 2000);
        // 业务逻辑...
    } catch (error) {
        log.error("执行出错: " + error.message);

// 3. 使用IIFE包装返回Promise

```

**模块加载验证**:

function checkModulesLoaded() {

            return false;

        log.debug(`模块 ${moduleName} 类型: ${moduleType}`);

## 13. 常见运行时错误和解决方案

基于AutoCommission项目的bug修复经验，以下是BGI脚本开发中最常见的运行时错误及其解决方案：

### 13.1 常量未定义错误

```javascript
// ❌ 错误示例：使用未定义的常量
var commissionsDataPath = Constants.COMMISSIONS_DATA_PATH; // 如果未定义会报错
var commissionsContent = file.readTextSync(commissionsDataPath);
```

**错误信息**: `Cannot read property 'COMMISSIONS_DATA_PATH' of undefined`

**解决方案**: 确保所有使用的常量都在constants.js中完整定义

```javascript
// ✅ 正确做法：在constants.js中完整定义所有常量
var Constants = {
  COMMISSIONS_DATA_PATH: "Data/commissions_data.json",
  COMMISSIONS_REPORT_PATH: "Data/commissions_report.txt",
  // ... 其他常量
};
```

### 13.2 数据文件格式不匹配错误

// ❌ 错误的数据文件格式

### 13.4 模块加载作用域错误

## 总结

BGI JavaScript脚本环境是一个高度安全的沙箱环境，限制了大部分可能造成安全风险的功能。基于AutoCommission项目的技术发现，开发者应该：

1. **使用BGI提供的API**: 优先使用`log`、`notification`、`file`、`genshin`等BGI提供的对象
2. **避免依赖标准Web API**: 不要使用`fetch`、`XMLHttpRequest`、DOM操作等浏览器API
3. **遵循模块化规范**: **必须使用`var`声明模块**，顶层直接eval加载，IIFE包装返回
4. **理解作用域限制**: 理解const/var的根本性差异和BGI引擎的执行机制
5. **遵循安全限制**: 理解文件访问、路径限制等安全机制
6. **做好兼容性检查**: 使用功能检测而不是假设某个API存在

**BGI脚本开发的三大核心要求** (基于AutoCommission项目发现):
1. **变量声明**: 模块必须使用`var`而非`const`声明
2. **模块加载**: 顶层直接eval，避免任何函数包装
3. **返回值**: 使用IIFE包装return语句返回Promise

通过遵循这些限制和技术要求，可以编写出稳定、安全、兼容性良好的BGI JavaScript脚本。

**重要参考**: [AutoCommission 模块化重构项目](./jscode/AutoCommission/README_REFACTOR.md) - BGI JavaScript脚本模块化开发的完整案例和技术指南。
