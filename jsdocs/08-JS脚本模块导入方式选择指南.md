# BGI JavaScript脚本模块导入方式选择指南

## 问题背景

在重构AutoCommission项目时，我们遇到了模块加载失败的问题，经过深入研究发现了BGI ClearScript V8引擎中JavaScript变量声明和作用域的根本性技术限制。

## 重大技术发现：const/var作用域差异

**突破性发现** (2025.07.24): BGI ClearScript V8引擎中，`const`和`var`声明在eval上下文中具有完全不同的作用域行为。

### 核心技术验证

通过AutoCommission项目的实验验证，我们发现：

```javascript
// ✅ var声明 - 可以跨作用域访问
eval('var Constants = { VERSION: "1.0.0" };');
log.info("Constants类型: " + typeof Constants); // "object" - 成功！

// ❌ const声明 - 无法跨作用域访问  
eval('const Constants = { VERSION: "1.0.0" };');
log.info("Constants类型: " + typeof Constants); // "undefined" - 失败！
```

**实验结果对比**:
```
✅ var声明模块: Constants(var)类型: object, Constants.VERSION: 0.98.11
❌ const声明模块: Constants(const)类型: undefined
✅ var基础类型: TEST_VAR类型: string, TEST_VAR值: test_var_value
❌ const基础类型: TEST_CONST类型: undefined, TEST_CONST访问失败
✅ function声明: testFunction类型: function, testFunction调用: function_works
❌ const对象: TEST_OBJECT类型: undefined, TEST_OBJECT访问失败
```

### 技术原理分析

**BGI ClearScript V8引擎特性**:
- `var`声明的变量会被注入到全局作用域，可跨eval上下文访问
- `const`声明的变量受到严格的作用域限制，无法跨eval上下文传递
- `function`声明具有最好的跨作用域支持
- 任何函数包装都会创建独立的执行上下文，导致变量隔离
- 顶层作用域不能直接使用return语句，会产生语法错误

## BGI支持的模块导入方式

### 1. eval() + var声明方式（推荐）

这是经过实战验证的稳定模块导入方式：

**正确的模块声明**:
```javascript
// lib/constants.js
var Constants = {
  VERSION: "1.0.0",
  BUILD_TIME: "2025.07.24"
};
```

**正确的模块加载**:
```javascript
// main.js - 必须在顶层直接执行eval
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));
eval(file.readTextSync("lib/ui.js"));

// 现在可以直接使用所有模块
log.info("版本: " + Constants.VERSION);
```

**错误的模块声明**:
```javascript
// ❌ 这些方式在BGI环境中都会失败
const Constants = { /* ... */ };           // const声明无法跨作用域
let Constants = { /* ... */ };             // let声明同样受限
export const Constants = { /* ... */ };    // ES6模块不支持
module.exports = { /* ... */ };            // CommonJS不支持
```

### 2. CommonJS require() 方式（不可用）

虽然BGI理论上支持CommonJS，但在实际项目中经常出现兼容性问题：

**理论支持**:
```javascript
const utils = require('./lib/utils');
const ocr = require('./lib/ocr');
```

**配置要求**:
```json
{
  "library": ["lib", "modules", "utils"]
}
```

**实际问题**:
- 版本依赖性强
- 配置复杂容易出错
- 实际使用中经常出现"require is not defined"错误

## BGI脚本的完整技术要求

基于AutoCommission项目的技术发现，BGI JavaScript脚本必须遵循以下技术要求：

### 1. 模块声明规范
```javascript
// ✅ 正确方式 - 使用var声明
var ModuleName = {
  method1: function() { /* ... */ },
  method2: async function() { /* ... */ },
  property: "value"
};
```

### 2. 模块加载规范
```javascript
// ✅ 正确方式 - 顶层直接eval
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));

// ❌ 错误方式 - 任何函数包装都会失败
try { eval(file.readTextSync("lib/module.js")); } catch {}
(function() { eval(file.readTextSync("lib/module.js")); })();
function loadModule() { eval(file.readTextSync("lib/module.js")); } loadModule();
```

### 3. 脚本返回值规范
```javascript
// ✅ 正确方式 - IIFE包装return语句
(async () => {
  return await Main();
})();

// ❌ 错误方式
return Main();                 // 顶层return语句，语法错误
Main();                        // 返回VoidResult，类型转换失败
```

## 技术对比

| 特性 | var+eval方式 | CommonJS方式 | const+eval方式 |
|------|-------------|-------------|-------------|
| 兼容性 | ✅ 所有版本 | ❓ 特定版本 | ❌ 不支持 |
| 配置复杂度 | 🟢 简单 | 🟡 中等 | 🟢 简单 |
| 作用域支持 | ✅ 全局可访问 | 🟡 模块作用域 | ❌ 作用域隔离 |
| 实际使用 | 🟢 广泛使用 | 🔴 很少使用 | 🔴 无法使用 |
| 稳定性 | 🟢 高 | 🟡 待验证 | 🔴 不稳定 |

## 最佳实践指南

### 推荐的项目结构
```
MyScript/
├── manifest.json          # 项目清单
├── main.js               # 主入口文件
├── lib/                  # 核心库文件
│   ├── constants.js      # var Constants = {}
│   ├── utils.js         # var Utils = {}
│   └── ui.js            # var UI = {}
└── data/                # 数据文件
```

### 标准模板

**模块文件模板**:
```javascript
// lib/utils.js
var Utils = {
  sleep: function(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
  },
  
  delay: async function(min, max) {
    const ms = Math.random() * (max - min) + min;
    return this.sleep(ms);
  },
  
  outputVersionInfo: function(version, buildTime) {
    log.info(`脚本版本: ${version} (${buildTime})`);
  }
};
```

**主文件模板**:
```javascript
// main.js
log.info("开始加载模块...");

// 1. 顶层直接eval加载所有模块
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));
eval(file.readTextSync("lib/ui.js"));

log.info("所有模块加载完成");

// 2. 模块加载验证
function checkModulesLoaded() {
  const requiredModules = ['Constants', 'Utils', 'UI'];
  const missingModules = [];
  
  for (const moduleName of requiredModules) {
    try {
      const moduleType = eval("typeof " + moduleName);
      if (moduleType === 'undefined') {
        missingModules.push(moduleName);
      }
    } catch (error) {
      missingModules.push(moduleName);
    }
  }
  
  return missingModules.length === 0;
}

// 3. 主程序逻辑
const Main = async () => {
  try {
    if (!checkModulesLoaded()) {
      log.error("模块加载失败，脚本终止");
      return;
    }
    
    log.info("版本: " + Constants.VERSION);
    await Utils.delay(1000, 2000);
    // 业务逻辑...
    
  } catch (error) {
    log.error("执行出错: " + error.message);
  }
};

// 4. 使用IIFE包装返回Promise
(async () => {
  return await Main();
})();
```

## 常见问题排查

### 问题1: "Module is not defined"
- **原因**: 使用了`const`声明模块
- **解决**: 改为`var`声明：`var ModuleName = { ... }`

### 问题2: "Illegal return statement"
- **原因**: 在顶层作用域直接使用return语句
- **解决**: 使用IIFE包装：`(async () => { return await Main(); })()`

### 问题3: "Unable to cast VoidResult to Task"
- **原因**: 脚本的最后一个表达式未返回Promise对象
- **解决**: 确保IIFE是文件的绝对最后一个表达式，所有执行逻辑都在IIFE内部

**详细分析**（基于AutoCommission项目技术发现）:
```javascript
// ❌ 错误结构 - IIFE提前结束，log语句在外部执行
(async function () {
  // 主要逻辑
})(); // IIFE结束

log.info("模块化主文件加载完成"); // 这成为脚本最后表达式，返回VoidResult！

// ✅ 正确结构 - 所有逻辑都在IIFE内部
(async function () {
  // 主要逻辑
  log.info("模块化主文件加载完成"); // 在IIFE内部
})(); // 这是文件的最后表达式，返回Promise
```

**根本原因**: BGI V8ScriptEngine期望脚本返回Promise对象用于Task转换。当log语句在IIFE外部执行时，它成为脚本的最后表达式，返回VoidResult而非Promise，导致类型转换失败。

**BGI脚本架构标准**:
```javascript
// 1. 顶层模块加载（BGI要求）
eval(file.readTextSync("lib/constants.js"));
eval(file.readTextSync("lib/utils.js"));

// 2. 函数定义区域（必须在IIFE之前）
async function executeMainProcess() {
  // 主要业务逻辑
}

// 3. IIFE作为最后表达式（关键）
(async function () {
  try {
    // 所有执行逻辑在此
    await executeMainProcess();
    log.info("执行完成"); // 必须在IIFE内部
  } catch (error) {
    log.error("出错: " + error.message);
    throw error;
  }
})(); // 必须是文件的绝对最后一个表达式
```

### 问题4: 模块加载成功但运行时报错
- **原因**: 使用了函数包装导致作用域隔离
- **解决**: 直接在顶层使用eval，避免try-catch或函数包装

## 迁移指南

### 从const声明迁移到var声明

**旧代码**:
```javascript
// ❌ 不工作的代码
const Constants = {
  VERSION: "1.0.0"
};

const Utils = {
  method: function() {}
};
```

**新代码**:
```javascript
// ✅ 工作的代码
var Constants = {
  VERSION: "1.0.0"
};

var Utils = {
  method: function() {}
};
```

### 从CommonJS迁移到eval方式

**旧代码**:
```javascript
// ❌ 可能不工作的代码
const utils = require('./lib/utils');
const constants = require('./lib/constants');
```

**新代码**:
```javascript
// ✅ 稳定工作的代码
eval(file.readTextSync("lib/utils.js"));      // 定义var Utils = {}
eval(file.readTextSync("lib/constants.js"));  // 定义var Constants = {}
```

## 总结

基于AutoCommission项目的深入研究，我们确立了BGI JavaScript脚本模块化开发的标准模式：

1. **模块声明**: 必须使用`var`而非`const`声明
2. **模块加载**: 顶层直接eval，避免任何函数包装
3. **返回值**: 使用IIFE包装return语句
4. **错误处理**: 依赖BGI引擎的内置错误处理机制

这套技术方案已在AutoCommission项目中得到验证，为所有BGI JavaScript脚本项目提供了可靠的技术基础。

AutoCommission项目成功展示了这套技术方案的应用：

- **技术突破**: 解决了BGI环境下的根本性作用域问题
- **实战验证**: 通过完整的测试验证了技术方案的可靠性
